# Linux 导出安全、缓存与 PDF 集成验收

## 范围与结论

第三阶段保留前两轮并发隔离、worker 超时、singleflight、MTEF/向量 WMF、真实几何基线和混合长除法完整预览修复。最初上游基线为 `bf56c59bc823a8a1bab518b4bc3a3d13d1a113d5`。

已实施三类收尾：

1. 配图只可来自明确授权根目录，真实 PNG/JPEG 验证、字节/像素限额，失败明确中止，不再读取任意本地文件或静默删图
2. 内存加权 LRU 与磁盘配额/TTL/所有权隔离，保留渲染与单次合并正确性，提供统计
3. 显式可启用的 Linux PDF HTTP 路由，包含原生对照、兼容基线、并发限制、超时与私有进程组清理

这里只证明所列 Linux 环境、配置和合成/仓库公开样本通过，不代表全平台或任意输入的认证。

## 兼容变化与配置

### 配图

默认无 `paperword.assets.root` 时含图片的请求失败为 `IMAGE_ASSET_DISABLED`（HTTP 503）；无图片文档仍可导出。必须由运维指定只含可导出图片的窄目录，建议只读挂载。参数与完整迁移说明见 `docs/image-assets-security.md`。

- 相对路径从允许根解释；绝对路径须同时通过路径边界与 realpath 边界
- `..`、UNC、URL、驱动器相对路径、越界路径、符号链接、FIFO/设备/非 regular 文件拒绝
- 历史 Windows 路径只按显式 `paperword.assets.windows-prefix` 完整前缀映射，不猜文件名或 suffix
- 默认每图 16 MiB / 16,000,000 像素；真实 PNG/JPEG 头尺寸先检查，随后 CRC/完整解码，嵌入同一字节快照
- 扩展名和客户端 MIME 不决定实际格式；坏图/缺图不转成 200 缺内容
- 普通常规 Windows filesystem provider 无 SecureDirectoryStream，会明确失败关闭；本次只验证 Linux 上的旧 Windows 路径映射

安全边界：资产树和配置必须由可信运维管理，不能让不可信本地进程并发替换目录项。标准 Java 没有把 regular-file 校验与 O_NONBLOCK 打开合成同一个原子操作，因此不宣称防御同权限恶意文件系统写者制造的 FIFO/ABA 竞态。每图限额也不等于总文档/全并发内存限额，生产仍需入口和容器资源控制。

### 缓存

见 `docs/render-cache.md`。默认内存 64 MiB / 2048 条，PNG/WMF 使用同一权重预算；磁盘 256 MiB / 8192 条，单条 16 MiB，写后 7 天过期、60 秒维护。`cache.enabled=false` 保持旧语义，仅禁用磁盘；内存容量设 0 才禁用内存保留。

磁盘数据写入独立 `paperword-formula-cache-v1` 有标记的目录，原子记录/校验和、进程锁和索引版本同步。只清理应用记录和过期临时文件，不清理普通文件或旧版散落缓存。旧文件需运维确认归属后另行处理，不计入新 namespace 的配额。配额限制已保留记录；暂存发布、执行中的渲染/响应、caller 引用不是保留缓存。磁盘安全 API 不支持时仅禁用磁盘，渲染和有界内存仍正常。

GET `/api/export/cache/status` 返回无公式内容、无服务器路径的计数；磁盘 TTL 由访问触发维护，闲置时不启动常驻扫盘线程。

### PDF

见 `docs/linux-pdf-service.md`。默认关闭；显式配置可信 helper/UNO jar 后启用：

- POST `/api/export/pdf`，JSON 同 `/word`
- POST `/api/export/layout-pdf`，JSON 同 `/layout-word`
- `mode=compatible` 默认；`mode=native_layout` 保留原生 LO 对照
- 默认并发 1、满时立即 429；转换默认 120 秒总 deadline（编译/启动/转换），DOCX 构建本身不在这条 deadline 内
- 生成 DOCX 上限 32 MiB、PDF 64 MiB，均可配；无公式文档允许正常导出
- 依赖缺失/禁用503、输入/输出超限413、转换不支持422、超时504；图片错误统一400/413/503

每任务独立 profile，UNO 仅 loopback，宏与外链更新关闭、外部包关系拒绝。服务用 setsid 私有进程组，并在 finally 用 `/bin/kill` 覆盖已脱离 launcher 的 LO 子进程；清理临时解除线程中断后恢复标志。日志最多64KiB。CLI 只有所有校验和源 SHA256 不变检查通过后才发布两份 PDF；失败仅留诊断日志。源 DOCX 永不保存重写。

源 DOCX 仍有原始可编辑 OLE/MTEF 和向量 WMF。当前 LibreOffice 在原生和兼容路径都会把公式预览栅格化到 PDF（约300dpi），不是新增兼容器转换为位图，不能称最终 PDF 全矢量。Word/MathType 原生 GUI 编辑并保存重开仍未验收。

### 暖 DOCX 回退定位：热身不足，而非已证明的稳态缓存成本

保留上述原始3次导出数据，没有删去不利结果。追加独立探针使用3对交替JVM、每类型10次热身再20次测量，计时仅`service.export`，每轮同时记录线程/进程CPU、分配量、GC与CompilationMXBean。

- 后半10轮的3fork中位数：重复40题63.49→64.76ms（+2.00%）；不同式40题111.58→109.14ms（−2.19%）
- 全20轮：+8.02%、+3.95%，逐轮仍有加速且前后分布重叠
- 测量阶段JIT累计编译时间约3596–5225ms；这是CompilationMXBean累计编译耗时，不等同单请求CPU
- after每fork实际1600次内存命中，0新增miss/淘汰/MathJax请求；磁盘已关闭，无配图所以无资产IO
- 240份合成DOCX、9600个OLE/MTEF/纯矢量WMF全部验证，前后对应OLE与预览字节相同

这些结果不支持“加权LRU/图片策略造成19–43%稳态退化”的判断。原3次只代表热身中性能，不能拿来宣称稳态吞吐退化。没有为未复现的问题撤销安全策略或增加冒险优化；也不把此次短测试当长期SLA保证。可使用 `scripts/linux-review/run_warm_docx_probe.py` 在目标部署复测。

## 新模板发现的历史字体缺字与修复

独立真实验收新增仓库六题 `exam-template.json` 时，HTTP200且DOCX文本完整，但原生与旧兼容PDF前两个节标题丢掉中文前缀。进一步用此前阶段的类重生成并真实转换，标题XML完全相同且同样丢字，确认这是原有Linux字体fallback缺陷，不是本轮安全策略引入。

UNO模型保持完整文本，但缺失宋体被LO错误回退到Mongolian。最终兼容路径在输出原生对照后，对缺失的CJK字体做显式、可配置、经可用字体清单验证的回退（默认Noto Serif CJK SC）；保留已安装字体及Latin/complex字体、全部字号和原始OLE尺寸。正文/表格/页眉页脚文字不重写，动态页码字段不替换。缺字体/无法安全解析字体名称时明确依赖错误，不猜。

模板因此自然重排为2页，三个节标题完整，39个OLE及原DOCX SHA保持不变。没有压缩字号或行高挤回不完整的原1页。原生对照仍真实展示LO缺字/基线限制，推荐交付使用明确的兼容路径。
